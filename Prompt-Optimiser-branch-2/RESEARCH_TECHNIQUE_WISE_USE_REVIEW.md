# PromptOptimizer — Research Technique Use Review

## Scope and bottom line

This is a documentation-only audit of the implementation and research notes in this workspace. It does not change or execute application code, tests, fixtures, model calls, or user files. The source documents are secondary summaries: the underlying papers and SLP3 scans are not available here, so paper-specific claims below are attributed to those notes rather than independently verified.

**Bottom line:** the project uses a sensible conservative foundation—source-located profiling, reversible text cleanup, lexical whole-unit ranking, hard keeps, dependency closure, recounting, validation, and restore/fallback. Those mechanics are not evidence that the optimizer preserves downstream task quality. Several familiar algorithms are only approximate adaptations, their weights and rules are uncalibrated, and the current evaluation does not establish that the combination beats simpler baselines at the same actual token budget. The project is not yet a research-validated semantic compressor or a general file-format converter.

The right immediate course is **KEEP** the deterministic, reversible safety framework; **FIX** the evaluation and label terminology; **IMPROVE** profiling, segmentation, retrieval, and selection using ablations; **EXPERIMENT** with more advanced approaches only after that baseline; **DEFER** costly/model-dependent techniques until they can be evaluated; **REMOVE** no current technique based on the available evidence.

## Evidence and how to read the assessment

- **Implemented** means there is an identifiable code path. It does not mean empirically useful.
- **Partial** means the implementation covers a narrow approximation or only part of the end-to-end idea.
- **Absent** means no corresponding implementation or evidence was found in the inspected project.
- **Keep / Fix / Improve / Experiment / Defer / Remove / Not applicable** are recommendations, not claims about completed work.
- Mechanism-level tests can verify deterministic behavior, invariants, and outputs for selected examples. They do not prove relevance, semantic preservation, or task success.
- The prior [RESEARCH_IMPLEMENTATION_AUDIT.md](./RESEARCH_IMPLEMENTATION_AUDIT.md) groups the supplied ideas into 48 *concept clusters*. That is a useful taxonomy, not a count of 48 separately implementable techniques or 48 independently completed features. This review uses broader technique families instead of treating cluster count as a progress metric.

| **Task-aware profiling** (project knowledge base; retrieval/query-focus proposals) | `RuleBasedTaskProfiler.profile` extracts explicitly labelled sections and falls back to a narrow imperative pattern. It records source spans and warnings. `ProfileSegmenter` uses extracted spans for prompt units; attachments in `PipelineDemo` use `ParagraphSegmenter`. | A useful offline starting point, but labels and imperative cues are not a general task parser. Tests establish examples and source partitioning, not extraction accuracy or task-family coverage. | **IMPROVE.** Add a manually reviewed, family-stratified profiling set; measure extraction precision/recall and query ablations. Multiple defenses reduce certain omission risks but do not validate semantic correctness. | **KEEP / IMPROVE.** Preserve fail-safe treatment for explicit constraints and exact values; measure false negatives and token overhead on adversarial/minimal-pair cases before changing thresholds. |

Candidate generation is safe because it does not claim equivalence or remove content. The tests verify ranking, tie order, and candidate generation—not that the blend beats BM25 alone. | **KEEP candidate-only duplicate analysis; EXPERIMENT with the blend.** Compare BM25-only, Jaccard-only, and blend at identical budgets; do not describe the combined score as validated semantic relevance. |

## Combination analysis

The current end-to-end chain has both useful safeguards and failure propagation:

1. **Profile → segment → score.** `RuleBasedTaskProfiler` supplies source ranges, `ProfileSegmenter` turns some prompt spans into typed units, and attachments use paragraph units. Profiling mistakes can therefore both mis-type content and bias the query. A narrow query may miss a useful attachment; a broad/misclassified task can promote irrelevant text.
2. **Protection + ranking.** HARD spans are masked from lexical scoring but any unit intersecting one is required. This appropriately avoids rewarding exact values as topical keywords, but means protection is an independent retention gate, not a relevance score. Broad protected sentences can keep much more than the span itself.
3. **Dependencies + greedy selection.** Dependency closure can add required units when considering a candidate. Fixed category passes and heuristic priors can nevertheless force poor tradeoffs, and a regex false negative may leave a real dependency unmodeled. Exact assembled recounts ensure the accepted candidate meets the supplied budget; they do not ensure best utility per token.
4. **Validation + restore.** Fresh span checks and restore-only recovery catch certain omitted source units. Semantic/fact/probe checks are explicitly NOT_RUN, so passing mandatory deterministic checks does not prove equivalence. If a necessary fact was not annotated and no deterministic check detects its loss, recovery has no signal to restore it.
5. **Format routing + lossless edits.** Conservative prose-only whitespace operations are a reasonable guardrail. Extension routing and Markdown wrappers are not extraction or conversion; do not infer structural correctness for code, CSV, JSON, logs, or PDF from successful text assembly.

**Overall combination verdict:** coherent as a conservative prototype, but not yet shown to be better than no-op, random, or simpler lexical selection at equal token budgets. The safest properties are mechanical (reversibility, exact recount where configured, deterministic checks); the least substantiated are the semantic value estimates and their benefit to the final answer.

## Priority actions

1. **FIX — gold-label evaluation before adding advanced compression.** Annotate each case with versioned task family, required facts, constraints/negations, exact values, and relevant source units. Avoid substring-only scoring; report per-label outcomes and clearly mark labels that require human judgment.
2. **FIX — precisely name current techniques.** Describe BM25+Jaccard as an unvalidated lexical heuristic; fixed-priority greedy budget selection as such; regex dependency inference as lexical; output Markdown assembly as framing rather than conversion. Keep `NOT_RUN` checks distinct from passing checks.
3. **IMPROVE — measure the safety/utility tradeoff.** Include exact-value and protected-span recall, false-positive retention/token overhead, dangling dependency rates, budget compliance, compression ratio, and a safe downstream task score. Report per-task-family results, not only pooled counts.
4. **EXPERIMENT — ablate one decision at a time.** Compare BM25, Jaccard, their blend, a TF-IDF/cosine baseline, and non-semantic controls before adding embeddings or learned pruners.
5. **DEFER — advanced/model- and modality-specific methods.** RST, embeddings, LLMLingua, LongLLMLingua, OCR, and AST transforms have additional dependencies, privacy/safety concerns, or task-transfer risk. Add them only as isolated arms with explicit costs and suitable checks.
6. **KEEP — conservative guardrails and recoverability.** Retain source provenance, whole-span exactness, reversible edits, deterministic ordering, original-input fallback, and refusal when no safe output fits.
7. **REMOVE — none recommended from this audit.** No available evidence justifies deleting the current safe scaffolding. If an ablation shows a heuristic adds no value or causes harm, disable that heuristic rather than removing unrelated recovery guarantees.

## Proposed matched-budget experiment

Run an offline optimizer-only stage first; do not claim answer quality from optimizer-only metrics.

### Arms

- Original / no-op.
- Random eligible-unit selection (seeded).
- Current fixed-priority selector with BM25+Jaccard.
- Current selector with BM25 only.
- Current selector with Jaccard only.
- TF-IDF/cosine lexical baseline.
- Optional oracle upper bound using gold-relevant units, clearly labeled as an unattainable ceiling.

Keep the tokenizer, source segmentation, hard constraints, dependency graph, assembler, and validator identical across arms. Evaluate the same cases at multiple **identical actual token budgets**, counting the final assembled representation with the target counter where consented and available. If only a heuristic counter is used, label the measurements estimates and do not report them as target-model token limits.

### Cases and outcomes

- Create versioned, family-disjoint train/dev/test partitions with human-reviewed gold units and labels for task, requirements, constraints, negations, exact numbers/identifiers, and output format.
- Include adversarial/minimal pairs: flip a negation, alter a numeric bound, change a path or identifier, move a constraint into an unlabeled section, and vary repeated/contextual code or log evidence.
- For retrieval, report gold-unit recall@k / recall under budget and ranking metrics. For compression, report labeled fact/constraint/exact-value preservation, false-positive retained tokens, budget compliance, and token ratio by family.
- Add downstream task scores only with a documented safe checker or a consented model evaluation that records model/version, prompt/template, usage, and failures. Compare compressed and original paired on the same task and target; do not execute arbitrary Java fixtures in-process.
- Use paired case-level comparisons, multiple seeds where randomness exists, confidence intervals, and per-family breakdowns. Report the quality-vs-token-budget Pareto curve rather than selecting one favorable budget.
- Include optimizer latency, provider token-count cost/transfer, generation cost where applicable, and net cost. A shorter prompt is not a cost saving if the optimizer's own cost exceeds the saved inference cost.

No experiment outcomes are available from this audit. The proposed arms are a protocol, not benchmark results.

## Differences from the earlier research implementation audit

- The earlier **48 clusters** are a deduplicated concept inventory. This review changes the presentation granularity to technique families; neither figure should be used as an implementation-completion percentage.
- “BM25/Jaccard implemented” and “partially implemented” can both be true at different levels. The scorer mechanics and deterministic examples exist; the end-to-end relevance method is still partial/unvalidated because its query, labels, calibration, and downstream benefit are not established.
- “Gold-label preservation metrics not implemented” needs a precise qualification: generic phrase/substring counts and metric-row fields exist, but **gold-label** preservation metrics do not. This review treats the current counts as weak proxies, not as evidence that no evaluation code exists.
- “Adaptive budget controller partially implemented” is liable to overstate progress. A numeric budget is enforced with greedy fixed priorities; no adaptive/task-specific budget policy is implemented.
- “Dependency-aware selection partially implemented” does not mean Java semantic dependency analysis; it means regex and simple structural lead-in inference with closure and validation.
- RST, TF-IDF/cosine, embeddings, token-pruning methods, OCR, Java AST transforms, and benchmark reproductions remain absent regardless of whether they appear in research notes or a roadmap.
